# OozoAI AI development guide

## Preserve the foundation

Read package.json, components.json, template.json and existing source before editing. Preserve existing version declarations, framework choices, working components and dependency notices. Use Node 24.22.2 and pnpm 10.34.4 without rewriting global tools. Read relevant installed framework docs under node_modules/next/dist/docs: this Next release differs from older versions. The canonical workflow uses pnpm-lock.yaml; the original npm lockfile is retained unchanged.

## Next.js and React

Use src/app App Router conventions: folders are route segments, page.tsx renders and layout.tsx composes. Keep pages/layouts Server Components by default. Add loading.tsx, client error.tsx and not-found.tsx where useful. Cache Components is enabled: consult current docs before choosing cache/dynamic directives, and do not add incompatible legacy route flags. Use the Metadata API for descriptive titles/descriptions; do not invent a public origin or fake SEO claims.

Keep "use client" at the smallest boundary needing hooks, event handlers, context or browser APIs. Pass serializable values from the server. Keep secrets, authorization and privileged SDKs on the server; never import server-only modules into client components. Use type-only imports. Do not read window/localStorage during SSR. Preserve next-themes hydration handling without suppressing unrelated hydration errors.

## Structure and types

Use @/_ aliases for src/_. Own primitives in src/components/ui, composed examples in src/components/features, shared shell in src/components, hooks in src/hooks, configuration in src/config, contracts in src/types and validation/helpers in src/lib. Add directories only for implemented code. Tests live in tests. Use kebab-case filenames and PascalCase components. Keep TypeScript strict; validate unknown values before narrowing. Do not use any, ts-ignore, or lint disabling to conceal errors.

## Component strategy and Tailwind 4

Inspect existing src/components/ui first. Preserve original radix-nova style, aliases and tokens in components.json. Prefer shadcn/Radix before any other UI library. Discover installed CLI commands with `pnpm exec shadcn --help` and `pnpm exec shadcn info`. Install only missing components with `pnpm exec shadcn add <component>` from the official ui.shadcn.com registry. Review generated source/dependency/lock diffs and never overwrite working components blindly. Do not execute arbitrary registry URLs or copy older template component files.

Tailwind 4 uses CSS imports and theme variables; do not add a v3 config. Use complete class strings and existing semantic tokens. Compose classes through @/lib/utils. Use native tables and small accessible SVG charts until real requirements justify a table/chart dependency. Do not install entire component collections or competing UI frameworks.

## Accessibility and responsive UX

Use semantic header/nav/main/sections, a clear heading hierarchy, links for navigation and buttons for actions. Provide visible labels, associated help/errors, aria-invalid and first-invalid focus. Support native constraints and shared form validation. Announce pending/success/error with concise live regions. Include readable loading, empty, error and disabled states rather than blank screens. Never fabricate customers, testimonials or business statistics; label example data.

Preserve Radix focus traps, Escape handling and focus return. Verify Tab, Shift+Tab, Enter/Space and keyboard menus. Icon-only controls need names; avoid nested interactive elements. Preserve skip link, visible focus, theme contrast and reduced-motion behavior. Start mobile-first, allow wrapping, and constrain horizontal overflow to a named table region. Test narrow/mobile and desktop widths plus light, dark and system themes.

## Forms, APIs and security

Current project state is ephemeral local UI. Authentication UI is a handoff example, not a login implementation. Never accept passwords into a demo handler or report fake account creation. Integrate a real provider with server-side session verification and authorization before protecting data.

Revalidate all untrusted bodies/query/header/file/upstream data at the server boundary; enforce sizes, content types and rate limits. Authorize each operation for user/tenant, deny by default, use parameterized queries, and secure HttpOnly/SameSite cookies and CSRF/origin checks appropriate to the session design. Keep errors safe; never reveal stack traces, secrets or request bodies. Avoid raw HTML, eval, shell interpolation, arbitrary redirects and unvalidated fetch targets/SSRF. UI validation does not replace server authorization.

No secrets belong in NEXT*PUBLIC* variables, browser props, logs or committed env files. .env.example is credential-free. Only configure exact trusted HTTPS iframe origins; default embedding is denied. HSTS is enabled only after HTTPS deployment. CSP allows framework/theme inline bootstrap; nonce-based CSP is a separate deployment change requiring dynamic-rendering tests. Keep analytics, remote fonts, tracking and update scripts absent by default. Document all opt-in outbound services/data flow in docs/security.md. No installation hooks.

## Performance and SEO

Keep static content server-rendered, interactive islands small, and dependencies justified. Use stable keys/derived state and avoid unnecessary effects, memoization or heavyweight UI data packages. Use named Lucide icon imports. System/local fonts avoid remote fetches. When adding images use next/image, intrinsic dimensions, sizes and explicit remote allowlists. Do not lazily hide meaningful first content without measured benefit.

Maintain Metadata API titles/descriptions and semantic content. Add canonicals/sitemaps/robots only after a real app origin and indexing policy are provided; never hardcode a personal domain. Use next/link for internal routes and noopener noreferrer for new-tab external links.

## Validation and delivery

Install via `corepack pnpm@10.34.4 install --frozen-lockfile`. Install Playwright Chromium explicitly once. Run `corepack pnpm@10.34.4 validate`: locked install, route type generation/TypeScript, ESLint, production build and unit/browser/accessibility/startup/HTTP checks. Fail on errors; do not disable tests or weaken assertions. Run dependency audit and review code/lockfile for secrets, network behavior and generated files. CI covers Windows and Ubuntu; never claim Ubuntu execution from Windows-only evidence.

Test API authorization/negative paths when adding a backend. Keep manifest, docs, commands and implemented capabilities consistent. Preserve existing dependency/runtime version declarations. The template release is separately versioned in template.json. Report executed checks and remaining limitations. Do not deploy or publish releases unless explicitly requested.
